# AI Support Widget self-service readiness review

23 November 2026 · Repository baseline `adb6ec2` · Public launch plan informed by the onboarding usability review

## Product verdict

Launch AI Support Widget publicly as **in-app support that can explain what happened in your product**. It uses an authenticated user's product state, recent activity, and application errors to diagnose issues and point to the evidence behind an answer. Tenant-scoped live lookups and user-confirmed actions extend that capability. Lead with the problem B2B SaaS teams already recognize: every failed import, permission issue, or account restriction that support has to send to engineering.

There are zero clients today. Launch the public site, interactive demo, open signup, one-command starter, and self-service production integration together. Everything from the demo to production use is free at launch. The team’s feedback shows why the starter belongs in that release: developers who downloaded the SDK and passed both supplied tests still had to build a page and supply their own reply to see the widget work. Build the launch campaign and production infrastructure in parallel. Track model consumption and operating costs internally through dashboards and alerts. Design the launch without enrollment, usage, or spend caps.

## The website and the first customer journey

**Homepage promise.** “AI support that knows what happened in your app.” Show a failed import, a grounded answer, and the evidence behind it. Make **Create a free workspace** the primary CTA, with **Try the demo** for visitors and **Run the starter** for developers. Include sign-in, docs, and a trust page. Explain what the widget can diagnose, the installation effort, the data it receives, and human handoff. Use clearly labeled synthetic scenarios and publish customer results once there are measurements and permission to share them. Offer English and Portuguese paths if both markets are in scope. Intercom already markets live data and actions, so show how well this product diagnoses failures inside a SaaS application and surfaces the evidence. [Intercom data connectors](https://www.intercom.com/help/en/articles/9916507-data-connectors-faqs)

**Launch and acquire customers.** Prepare direct outreach to SaaS support leads and technical founders, a public launch announcement, a short product walkthrough, and developer-facing examples. Send each channel directly to the demo or signup. Give prospects three demonstrations they can recognize: a failed import, missing permissions, and an account restriction. Offer help alongside self-service. Use launch-week funnel data and support questions to prioritize changes to the website, starter, and installation flow.

**Demo scenario.** Let a visitor try “Why did my import fail?” against a synthetic failed job, or choose a permission issue or an account restriction. Show the failed step, time, and reference ID behind the answer, then show a human handoff with the relevant context. Use a deterministic fixture for public visitors so the experience is fast and predictable. Give signed-up workspaces a sandbox that runs the real chat pipeline against synthetic data and records a first successful answer.

**Signup and workspace.** Verify the person's email through a managed identity provider, create an owner, workspace, and sandbox atomically, and start the onboarding checklist immediately. Use revocable sessions and keep machine credentials in the server-side installation flow. Keep platform operators in a separate console with named, MFA-protected access. Reuse the tenant model as the environment boundary. Ship staging and production connections, team invitations, named developer and support roles, and auditable membership changes. Treat existing test projects as compatibility checks for conversation identities, integration credentials, and SDKs.

**Try the widget.** Put this path beside **Connect my application** in the Quick Start. Ship one runnable Node reference app in the public kit, with a single documented command that starts it and prints the URL to open. Use the actual pinned SDK, compact synthetic context, a sample user, and a fixed local reply. Label where the reply came from, show the expected browser result, and provide Reset. Document the Node prerequisite, a clean install command if dependencies need installing, which files run on the server or in the browser, and exactly which routes and settings to replace. The public website demo can reuse the same scenario. Keep the SDK pin and checksum alongside the runnable example. [Downloads](web/src/app/developers/downloads/page.tsx) · [SDK manifest](web/public/widget.manifest.json)

**Connect my application.** Use the same starter to show a stepwise switch from local fixtures to a test tenant. Identify who can create the project and issue its scoped integration credential, and link to the relevant environment settings. Let customers resume at the next unfinished step. Provide a complete authenticated bootstrap route that demonstrates where to derive the signed-in user, request a widget session, and fetch authorized context. Let customers copy environment-specific config, verify the browser origin, keep the secret on the application server, and get a real model reply against synthetic context in staging. Publish the framework-neutral contract and a typed mapper with strict allowlists for product identifiers and error codes. Recommend minimal valid context and one meaningful signal, such as the last failed job. Provide explicit schema states for data that is absent or unavailable before making any of the currently required blocks optional. Keep MCP read-only setup after chat works. Offer signed writes after connector verification and customer acceptance. **Installation status.** Give customers a checklist that advances from workspace created to origin verified, session issued, widget connected, first grounded answer, and production enabled. Show the last successful check, SDK version, environment, retryable errors, and a copyable diagnostic reference. In the starter and hosted checklist, name the failed stage and next check. ## Widget fixes for launch

- **Preserve unsent messages and make retries safe.** The team forced a follow-up to return HTTP 503 and had to retype the message. The SDK clears the input before waiting for the API and appends the user’s message only on success. Keep the message editable or visibly marked as failed. Offer **Retry** and **Edit**, and pair Retry with a stable client-generated ID and server-side deduplication. Cover first turns and follow-ups, including a request the server persisted before the browser lost the response. Verify exactly one stored user message and one rendered copy when a retry succeeds. Scope drafts to the active identity and clear them on logout or identity change. [Chat send path](widget/src/chat.ts#L130) · [Gateway routes](server/src/modules/gateway/gateway.routes.ts#L40)
- **Apply `locale` to the whole interaction.** The team’s `pt-BR` screenshot shows Portuguese conversation text alongside English controls and error states. Use the selected locale for launcher and close controls, empty and loading states, send errors, rating, and accessible labels. Preserve keyboard focus when opening, Escape to minimize, and conversation state when reopening. Verify the full `pt-BR` journey with a Portuguese reader and run automated coverage for `en-US` as well. [Widget launcher](widget/src/widget.ts#L67) · [Chat controls](widget/src/chat.ts#L13) · [Current date localization](widget/src/evidence.ts#L26)
- **Let users close without rating.** Offer **Close without rating** after the resolution question, for both responses. The current SDK and API require a 1–10 value. Make the API field optional, accept existing scored requests, and store missing scores as `null`. Keep the resolution outcome available separately and calculate rating metrics from submitted scores. Verify that skipping closes the case in one request and that a failed close offers a retry. [Close flow](widget/src/chat-renderer.ts#L39) · [Close API](server/src/modules/gateway/gateway-extra.routes.ts#L10) · [Rating aggregation](server/src/modules/admin/analytics.service.ts#L111)

### Production architecture for launch

- **Separate capability from availability.** Knowledge retrieval and email, Jira, and Zendesk connectors have code and tests, but the main entry point wires neither the knowledge service nor escalation. Push context can already include a small knowledge pack. Offer simple customer-managed support material and a working human handoff first. Turn on one real helpdesk connector after tenant isolation, scoped configuration, delivery retries, and failure visibility are tested. The TrackShare progress record reports technical acceptance of one signed write operation using synthetic resources. Use it as integration evidence. [Runtime composition](server/src/index.ts#L37) · [Escalation contract](server/src/modules/gateway/gateway-extra.routes.ts#L54) · [TrackShare verification record](progress.txt#L484)
- **Protect chat throughput and action integrity together.** The runtime constructs an action service for all conversations. Its wrapper holds a PostgreSQL transaction and shared four-connection lock pool through model and MCP calls, even when a conversation has no actions configured. Scope locking to short state transitions or serialize eligible turns in durable workers, keep provider calls outside database transactions, and retain confirmation binding, persisted intent, and status reconciliation. Each turn can also read up to 20 prior cases with a separate message query for each. Bound this history at query and prompt time. MCP reconnects and lists tools within a turn. Measure the cost and reuse tenant and identity-scoped work where the provider contract permits. Harden and meter outbound connectors throughout. [Runtime composition](server/src/index.ts#L27) · [Turn wrapper](server/src/modules/actions/action-turns.ts#L3) · [Lock implementation](server/src/modules/actions/action-store.ts#L40) · [Conversation history](server/src/modules/gateway/case-history.ts#L87) · [MCP transport](server/src/modules/orchestrator/mcp-client.ts#L37)
- **Ground answers and measure actual outcomes.** Keep validated scoped context and deterministic authorization. Establish a labelled eval set for failed jobs, permissions, account restrictions, stale context, cross-user access, fabricated evidence, and provider outages. Test no-data responses and human handoff. Feed results into release checks for prompts, models, and connectors. Give customers timestamps and verifiable references. Send relevant context and track model cost and quality together. [System prompt](server/src/modules/orchestrator/system-prompt.ts) · [Response parser](server/src/modules/orchestrator/response-parser.ts) · [Tool orchestration](server/src/modules/orchestrator/tool-executor.ts)
- **Make the admin data path bounded and accurate.** The per-tenant cases endpoint returns an empty list because the entry point supplies no case-list callback. Tenant analytics loads whole case, message, and snapshot histories, and the session listing fetches messages separately for each case. Current resolution counts infer no human involvement from `resolved` status, and first-reply analytics uses resolved cases only. Return scoped case data with cursor pagination, distinguish empty states from errors, and define tenant versus aggregate metrics explicitly. Put aggregates in time-windowed queries or rollups and persist separate user-confirmed resolution, handoff, and reopen events. [Tenant cases route](server/src/modules/admin/admin.routes.ts#L152) · [Runtime wiring](server/src/index.ts#L62) · [Analytics](server/src/modules/admin/analytics.service.ts#L54) · [Database queries](server/src/shared/db-data-sources.ts#L48) · [Session listing](server/src/modules/admin/session-admin.routes.ts#L26)

Test that a clean download runs with the published commands and that its fixtures show the advertised result. Use browser checks of real setup, refresh, identity switching, handoff, failed SDK load, keyboard/mobile use, and accurate localized UI. Keep archived pull and JWT instructions out of the default discovery paths. The starter should target supported deployment URLs and test environments and ship as maintained, versioned code. Keep the current stack and split the public web assets, API, and turn workers operationally. Serve versioned assets from a CDN, use a production database with backups and a restore drill, and centralize structured metrics, traces, and logs. Separate liveness, readiness, and end-to-end synthetic checks. Use immutable releases, verified migrations, preproduction smoke tests, and a rollback path that preserves session and action security. Turn the team’s clean-machine exercise into a release check. Open the sample, create a free workspace, connect a staging project, diagnose an incorrect SDK path, and complete a production-like install with synthetic identities. Track site visits, demo starts, starter use, verified signups, staging replies, production installs, and live grounded replies. Use **time to first live grounded reply** as the activation metric and **workspaces with a confirmed helpful resolution each week** as the value metric. Track conversion by acquisition channel, diagnostic failures, handoff success, operator interventions, p95 response latency, and cost per successful conversation. Use the five-minute sandbox and 30-minute staging times as onboarding objectives. Start the staging clock when the developer’s environment is ready.

Use a prelaunch capacity scenario of 5,000 active workspaces × 10 conversations per day × 3 AI turns. That is 150,000 turns per day, about 17 turns per second at a 10× peak, and about 139 in-flight turns at an eight-second average. Test that load and bursts above it with multiple replicas and realistic provider delays. Measure queue recovery, database pool contention, tenant fairness, and the impact of a provider outage. Confirm live provider throughput and failover separately from synthetic load results. Use the measurements to provision workers, PostgreSQL, Redis, and model capacity for launch.
