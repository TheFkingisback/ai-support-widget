**SDK 0.3.0 · دليل الواجهة الخلفية، الواجهة الأمامية والتشغيل**

## 1. إزاي بيشتغل

الواجهة الخلفية بتاعتك بتوثّق المستخدم، بتعرض السياق المصرح بيه وبتصدر جلسة مدتها 15 دقيقة. في مكالمة الإصدار، ممكن تتضمن سيرفرات الـ MCP المتاحة للشخص ده. المتصفح بيستقبل الـ JWT بتاع الودجت والسياق.

## 2. البيئات والمسؤولين

المنصة موجودة على https://support-ai.pontes.uk. استخدم بيانات اعتماد التكامل للبيئة الصحيحة. مسؤول مساحة العمل بيحصل على بيانات الاعتماد من لوحة التحكم. فريق التطبيق بيحافظ على التمهيد الموثّق، السياق والرموز المميزة المفوضة لكل مستخدم وسيرفر.

## 3. بيانات الاعتماد

| بيانات الاعتماد | الوجهة | الاستخدام |
| --- | --- | --- |
| بيانات اعتماد التكامل sik_ | Support AI | إصدار جلسة في الواجهة الخلفية |
| رمز مفوض لكل سيرفر | MCP المشار إليه في الجلسة | استدعاء الأدوات كشخص موثّق |
| JWT الجلسة | API الشات | فتح ومتابعة المحادثات في الودجت |

احفظ بيانات اعتماد التكامل في خزنة التطبيق. إلغائها بيعطّل الـ JWTs اللي تم إصدارها بيها في الطلب التالي. أنشئ الرموز المميزة المفوضة في الواجهة الخلفية وحدد كل واحد لمورد، مستخدم ومدة صلاحية.

## 4. تدفق التوثيق والهوية

```text
جلسة التطبيق الموثّقة
  → الواجهة الخلفية بتتحقق من الشخص النشط، المنظمة والصلاحيات الحالية
  → POST /api/widget/sessions مع sik_ على السيرفر
  ← jwt + tenantKey + expiresIn
  → الواجهة الخلفية بتجمع وبتعرض سياق نفس الهوية
  ← المتصفح بيستقبل الجلسة/السياق مع Cache-Control: no-store
  → الودجت بيستدعي /api/cases ومسارات المحادثة بالـ JWT المؤقت
```

الحفاظ على المعرف التاريخي `usr_...` للعميل بيمنع فقدان الوصول لمحادثاته الخاصة. لا تستخدم email، الدور، الجهاز أو الطابع الزمني كهوية. إذا كان نفس المستخدم ممكن يغير الشركة، حدد موضوع ثابت لكل ارتباط أو سياسة تاريخ صريحة؛ المنصة بتصرح بالمحادثات حسب المستأجر + الشخص، بدون استنتاج منظمات العميل.

المنصة بتتحقق من التوقيع، المصدر `ai-support`، الجمهور `ai-support-widget`، الغرض `widget`، `sub=userId`، الصلاحية وبيانات الاعتماد النشطة للجلسة. المتصفح لا يعيد التوقيع أو يغير المطالبات. الأدوار المرسلة للدعم هي معلومات سياقية؛ ترخيص الـ APIs/MCP بيستمر في سيرفر العميل.

## 5. عقد المصدر

```http
POST https://support-ai.pontes.uk/api/widget/sessions
Authorization: Bearer <SUPPORT_INTEGRATION_CREDENTIAL>
Content-Type: application/json

{"userId":"usr_usuario_autenticado","userEmail":"","userRoles":["member"],"plan":"standard"}
```

استجابة 200: `{"jwt":"<JWT>","tenantKey":"ten_do_projeto","expiresIn":900}`. تحقق من `tenantKey` قبل إعادتها للمتصفح. الملف `backend-session.mjs` بينفذ جسم صارم، مهلة، حظر إعادة التوجيه، حد الاستجابة والتحقق من المستأجر؛ لا يحل محل وسيط التوثيق الخاص بك.

| الحقل | القاعدة |
| --- | --- |
| mcpServers | قائمة اختيارية تصل إلى ثمانية كائنات مع id، url و accessToken فريدين. انظر القسم 12. |
| userId | إلزامي، تقليم، 1-200 حرف |
| userEmail | بريد إلكتروني صالح يصل إلى 254 حرفًا أو فارغ؛ الافتراضي فارغ |
| userRoles | حتى 30 سلسلة من 1-80 حرفًا؛ الافتراضي قائمة فارغة |
| plan | سلسلة من 1-80 حرفًا؛ الافتراضي standard |

متبعتش tenantId, tenantKey, userName, role, purpose, exp أو أي خانات تانية في الـ body. الـ credential هي اللي بتحدد الـ tenant. الهوية بتيجي من الـ session/database، مش من الـ query/body بتاع المتصفح. الـ issuer مبيقبلش JWT بتاع مستخدم، مفتاح إداري، أو سر قديم بدل `sik_`.

الـ issuer العام بيشتغل من غير حصص استخدام لكل مشروع. استخدم نفس الـ session لو لسه صالحة لنفس الشخص، الشركة، والصلاحيات، مع انتهاء صلاحية بدري وإلغاء صلاحية عند التغييرات.

## 6. سياق إلزامي وهوية صحيحة

كل حالة جديدة محتاجة `context.userState`, `context.userHistory` و `context.userLogs`. ابعت قوائم فاضية لما تكون المصدر اتسأل ومفيش سجلات؛ **متحولش مجموعة فشلت لقائمة فاضية تبان إنها نجحت**. لو مقدرتش توفر سياق صالح ومصرح بيه، الـ bootstrap بتاع العميل لازم يرجع خطأ متحكم فيه.

`context.example.json` هو المثال الأدنى. `context.schema.json` تم تصديره من الـ schema Zod المستخدم في السيرفر، مش مكتوب بشكل مستقل. تحقق من الـ JSON في الـ backend قبل النشر. أي خانات إضافية مش معروفة بيتم تجاهلها؛ الـ metadata والقواعد ممكن تحتوي على هياكل خاصة بيها، خاضعة للـ projection/limits. الـ schema مش بيثبت الصلاحية ولا بيشيل كل البيانات الحساسة.

| بلوك | إلزامي / هيكل |
| --- | --- |
| userState | userId, tenantId, roles, plan, featuresEnabled, entities, activeErrors, limitsReached |
| userHistory | windowHours إيجابي لحد 720، events؛ الـ timeline بيتبني تاني من events |
| userLogs | recentRequests, jobs, errors |
| knowledgePack | اختياري؛ docs مع id, title, content, category |
| businessRules | اختياري؛ كائن قواعد موافق عليه، متسلسل كـ runbook |

`userState.userId` لازم يكون هوية الـ user اللي تم إصدارها بالظبط. **`userState.tenantId` هو الـ tenant بتاع الـ platform**، مش الـ ID بتاع المنظمة/المحل في الـ client. أي اختلافات بترجع 403. البيانات في المتصفح ممكن تتغير؛ الـ context مش بيصرح بالعمليات.

## 7. الخانات، الحدود، والتوحيد

| هيكل | الخانات الأساسية / القواعد |
| --- | --- |
| entities | type, status؛ id/description اختياريين؛ metadata كائن؛ لحد 100 |
| activeErrors | errorCode, errorClass, retryable, userActionable, resourceId, occurredAt؛ لحد 100 |
| errorClass من activeErrors | validation, permission, infra أو business؛ فئات زي payment بتحتاج mapping |
| events | ts, event, page؛ elementId, intent, correlationRequestId بيقبلوا null/إهمال؛ لحد 1,000 |
| recentRequests | ts, route, httpStatus رقم صحيح، timingMs, requestId؛ errorCode/resourceId ممكن يكونوا null |
| jobs | jobId, queue, status, createdAt, updatedAt, durationMs رقم أو null؛ errorCode/lastStage ممكن يكونوا null |
| status من jobs | queued, running, succeeded, failed, canceled |
| errors من الـ backend | ts, errorCode, errorClass نص، route, requestId؛ resourceId ممكن يكون null |
| docs | لحد 50؛ content لحد 32,000 حرف، باقي النصوص لحد 4,096 |

التواريخ هي نصوص ISO-8601 مع timezone؛ اعمل serialize للـ Date في الـ backend. متخترعش updatedAt, durationMs, retryable أو فئات عشان تعدي الـ schema بس: استخدم المصدر الحقيقي أو اهمل السجل وبلغ عن عدم توفر المصدر. سجل الـ mappings الخاصة بمشروعك في الـ acceptance.

سقف السياق اللي اتبعت: **262.144 بايت UTF-8 (256 KiB)**. الـ HTTP الكامل لسه محدود بـ 1.048.576 بايت. ميزانية الـ snapshot هي `min(maxContextBytes, 262144)`. لو الجزء الأساسي ما كفاش، الطلب بيفشل؛ قلل الـ metadata/documents في الـ backend. بنقترح تبدأ بـ 48 KiB، عشر كيانات ومعرفة قصيرة.

الخادم بيفلتر الأحداث/الـ logs بأصغر نافذة بين المطلوبة والخاصة بالمستأجر، بيشيل التواريخ المستقبلية وبيطبق maxLogLines مدمج مع الـ requests، الأخطاء والـ jobs (بالترتيب ده). maxDocs بيحدد قائمة الـ docs؛ businessRules هو runbook منفصل وبيستهلك الميزانية الكلية برضه. الـ timeline بيمشي على الأحداث اللي فضلت. بيانات أقل ذات صلة غالبًا بتنتج تشخيص أفضل وتكلفة أقل.

## 8. الخصوصية والاستمرارية

صمم البيانات قبل ما تبعتها: ما تبعتش أبدًا headers، cookies، JWTs، بيانات اعتماد، strings اتصال، URLs موقعة، محتوى ثنائي، بيانات مستخدمين تانيين أو صادرات خام. استبدل الأسرار بمراجع دعم. ما تبعتش الـ PRD كله أو logs كاملة كقاعدة معرفة.

الـ snapshots الجديدة بتعدي على تحقق، تنقيح، تقليل وميزانية قبل التسجيل. الرسائل ونتائج الأدوات بيتم التعامل معاها بأنماط معروفة من الأسرار. الحماية دي تكميلية: مش مصنف لا يخطئ للبيانات الشخصية، مش بيصحح السجلات التاريخية بأثر رجعي ولا بيحل محل تصميم العميل.

السياق هو snapshot من بداية المحادثة، مش استعلام في الوقت الفعلي. بلغ عن الـ timestamps والمصادر. `updateContext()` صالح للحالة اللي جاية؛ للبيانات الحالية أثناء محادثة، استخدم أداة قراءة معتمدة.

## 9. الـ Frontend والـ SDK 0.3.0

قدم الـ SDK الثابت من الحزمة أو من الـ URL العام. راجع الـ SHA-256 مع الـ `widget.manifest.json`. تجنب الـ script المكرر، الإصدار العائم والـ cache بتاع الـ JWT. الـ controller المرجعي في `widget-controller.mjs` بيتركب بعد الـ bootstrap، بيستنى onOpen، بيجدد وبيمنع التركيب المتأخر بعد الـ logout.

```js
const controller = mountSupport({
  apiUrl: 'https://support-ai.pontes.uk',
  bootstrap: signal => fetchAuthenticatedBootstrap(signal),
  getContext: signal => fetchAuthorizedContext(signal),
  onUnavailable: () => showHumanSupportChannel(),
});
// عند الـ logout، تغيير الشخص/الشركة/الدور وتنظيف المكون:
controller.destroy();
```

الوظائف اللي فوق دي هي callbacks للتطبيق، هتتنفذ مع عميل الـ HTTP المعتاد بتاعك. الـ Bootstrap بيرجع `{jwt,tenantKey,expiresIn,context}`. الـ getContext بيرجع كائن السياق. في React، ثبت الـ callbacks بـ useCallback وركب في useEffect مرتبط بالهوية. ما تحطش الـ widget بره المنطقة الموثقة ولا تقدم زوار بـ userId مشترك.

الـ SDK بيقبل `onTokenRefresh` اللي بيرجع الـ JWT الجديد؛ بعد 401، بيكرر الطلب مرة واحدة. التجديد لازم يستخدم نفس الشخص. تغيير الهوية بيتطلب destroy و init. لو بتستخدم timer استباقي، يفضل حوالي عشر دقايق مع jitter وتلغيه في الـ cleanup. أخطاء الـ bootstrap، التجميع والنموذج ما ينفعش تعطل التطبيق الرئيسي.

## 10. الـ Logout، الصلاحيات والتاريخ

`destroy()` `destroy()` بيلغي المكالمات وبيشيل الثبات المحلي لكل مستأجر/شخص. ده مش إلغاء فردي على السيرفر. ممكن JWT اللي اتنسخ يفضل صالح لمدة تصل لـ 15 دقيقة بعد تسجيل الخروج/القفل على الكلاينت. لو محتاج إلغاء فوري لكل شخص، العقد بيتطلب تطوير إضافي؛ متستخدمش تدوير المستأجر بالكامل كـ تسجيل خروج عادي.

كل قراءة/كتابة للمحادثة بتتطلب نفس المالك والمستأجر. تغيير الدور في الكلاينت مش بيمسح المحتوى اللي الشخص استلمه بالفعل في المحادثة. حدد سياسة السجل لتقليل الصلاحيات وتغييرات المؤسسة. متخففش التفويض عشان تسترجع caseId قديم؛ تحقق من الموضوع الأصلي أو ابدأ محادثة جديدة.

## 11. CORS, CSP, PWA والوصول

اسمح للمنصة بالوصول الدقيق لكل واجهة أمامية. SDK بيحتاج connect-src للدعم؛ تقديم الملف المحلي بيسمح بـ script-src ذاتي. SDK بيحقن الأنماط في Shadow DOM ولسه مش بيستقبل nonce: وافق على سياسة CSP الحقيقية، وممكن تتطلب تطوير SDK للأنماط الخارجية/nonce/hash. متوقفش السياسة كلها.

الجلسات والسياق هما no-store. استبعد مسارات الدعم من ذاكرات التخزين المؤقت لـ PWA، واستمرارية الاستعلامات وأدوات إعادة التشغيل. اختبر لوحة المفاتيح، التركيز، قارئ الشاشة، التكبير/التصغير والموبايل. قدم قناة بشرية حقيقية في التطبيق، مع تأكيد الوقت/الرابط. SDK مش بيخترع مزود خدمة.

## 12. سيرفرات MCP في الجلسة

الباك إند بتاع التطبيق بيبعت `POST /api/widget/sessions` مع بيانات اعتماد التكامل `sik_`. بيستمد الشخص ومؤسسته من تسجيل الدخول وممكن يتضمن لحد تمن سيرفرات في `mcpServers`. الحقل المحذوف أو الفارغ بيعمل دردشة بسياق. كل جلسة جديدة بتاخد قائمتها الخاصة.

```json
{
  "userId": "usr_ana",
  "mcpServers": [
    {"id":"billing","url":"https://billing.example/mcp","accessToken":"TOKEN_DELEGADO_BILLING"},
    {"id":"crm","url":"https://crm.example/mcp","accessToken":"TOKEN_DELEGADO_CRM"}
  ]
}
```

كل id بيبدأ بحرف صغير وبيقبل حروف صغيرة، أرقام، شرطة سفلية وشرطة، لحد 32 حرف. الـ IDs، الـ URLs الموحدة والتوكنز فريدة في القائمة. النقل هو MCP Streamable HTTP على HTTPS عام، بورت 443، مع URL بدون بيانات اعتماد، استعلام أو جزء. الخدمة بتتحقق من DNS عند الاتصال وبترفض إعادة التوجيه.

التطبيق بيصدر أو بيحصل على توكن وصول قصير لكل وجهة، مقيد بالشخص، المؤسسة، الصلاحيات والجمهور بتاع MCP ده. Support AI بيقدم `Authorization: Bearer <accessToken>` للسيرفر المقابل. المزود بيتحقق من التوقيع أو الاستبطان، المصدر، الصلاحية، الجمهور والوصول للمورد في كل عملية. بينشر في الكتالوج الأدوات المسموح بيها للهوية دي بس. بيانات اعتماد المنصة، JWT بتاع الودجت ومفاتيح الخدمات زي Stripe ليها أغراضها الخاصة.

التوكن المفوض بيبقى مشفر على السيرفر لمدة تصل لـ 900 ثانية. المتصفح بيستقبل `{jwt, tenantKey, expiresIn: 900}`. عند التجديد، الباك إند بيعيد التحقق من الهوية وبيبعت قائمة جديدة بتوكنز صالحة. أي اقتراح اتعمل قبل التجديد لازم يتقدم تاني. لتغيير المؤسسة، استخدم معرف ثابت لكل رابط ودمر النسخة السابقة من الودجت.

الـ Support AI بيلف على صفحات الـ `tools/list`، وبيفرق بين الأسماء المتشابهة حسب السيرفر، وبيستخدم الاسم الأصلي لما بينادي الـ `tools/call`. الكتالوجات اللي فيها أكتر من 32 أداة بيكون فيها بحث وتقسيم صفحات جوه الشات. حدود الاكتشاف لكل سيرفر هي 128 صفحة و4 ميجابايت من الوصف. لو سيرفر فشل في الاكتشاف، الباقيين بيفضلوا شغالين.

الأدوات اللي فيها `annotations.readOnlyHint: true` ممكن تتسأل عنها مباشرة. لأي أداة مافيهاش الملاحظة دي أو الملاحظة غلط، الشات بيعرض السيرفر والاسم والحجج قبل ما ينفذ. اعلن عن القراءة فقط للعمليات اللي مالهاش تأثير على البزنس. المستخدم بيرد بـ `confirmar` أو `confirm` على الرسالة المعروضة في خلال خمس دقايق. الـ SDK بيبعت `replyToMessageId`. التأكيد ده بيكون صالح للحجج دي، والسيرفر، والجلسة، والمحادثة. أي اقتراح جديد بيحل محل اللي قبله.

المنصة بتعمل محاولة تنفيذ بعد تسجيل التأكيد وبتبعت `Idempotency-Key` مع الـ ID بتاع الاقتراح. بالنسبة للمدفوعات والعمليات اللي ليها تأثيرات خارجية، المزود لازم يحفظ المفتاح والنتيجة بشكل متكامل ويحترم مفاتيح الـ idempotency المطلوبة من الخدمة المالية. بعد الـ timeout أو النتيجة الغامضة، الدعم بيسجل حالة غير معروفة، وبيمنع أي تغييرات جديدة في المحادثة دي وبيخلي الاستعلامات متاحة. راجع العملية في النظام الأصلي قبل ما تكمل.

عشان تعتمد، اختبر جلسة من غير سيرفرات، جلستين لنفس المستخدم، منظمتين، سيرفرات فيها أدوات بنفس الاسم، وكتالوج متقسم صفحات. اتأكد من نطاق/انتهاء صلاحية التوكنز في المزود، والإلغاء، والتأكيد المكرر. استخدم سجلات مصطنعة عشان تتأكد من النتيجة في المصدر.

## 13. النموذج، الموجه، والمعرفة

الحفاظ على النموذج اللي تم اعتماده بالفعل من المشروع في البداية بيقلل من التغييرات المتزامنة. لتقييم جديد، `openai/gpt-4.1-mini` هو مرشح متوافق مع المعايير الحالية: Chat Completions عن طريق OpenRouter، ودرجة حرارة 0.3، و max_tokens 2048. لازم يتم التحقق في الحساب الحقيقي قبل التفعيل. Preferred Model له الأولوية على Model Policy؛ "auto" مش توجيه ذكي. الأسعار/التكاليف لازم تيجي من المزود؛ التقديرات القديمة من لوحة التحكم ممكن تختلف.

حقل **AI Instructions / Custom instructions** بيقبل لحد 2,000 حرف فعال. الصق `PROMPT-TENANT.txt` بس؛ راجع الأسماء، القناة، وقواعد المنتج. ماتلصقش بيانات اعتماد أو تجمع مستندات في الحقل ده. التعليمات دي بتكمل قواعد المنصة؛ مش بتدي تصريح ولا بتفعل أدوات.

الموجه اللي بيتم توفيره بيرشد الإجابات باللغة والكتابة اللي بيختارها الشخص، الحقائق منفصلة عن الفرضيات، احترام الأذونات، استخدام مراجع آمنة، عدم وجود وعود بأي إجراءات، وقناة بشرية. `knowledgePack.docs` لازم يحتوي على كتيبات تشغيل قصيرة ومحدثة مع تحديد المسؤول: الأخطاء المتكررة، التشخيص، حدود المنتج، وكيفية تأكيد النتيجة. السجلات والمستندات هي بيانات، مش تعليمات لتغيير قواعد المساعد.

مصادر النموذج: [OpenAI GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini) و [كتالوج OpenRouter](https://openrouter.ai/api/v1/models)، تم الرجوع إليها في التحضير السابق بتاريخ 14/09/2026. أعد تأكيد التوفر/الأسعار عند التنفيذ؛ لم تكن هناك مقارنة مدفوعة للنماذج في هذه المجموعة.

## 14. عقد الأخطاء والتشخيص

| الاستجابة | المعنى / الإجراء |
| --- | --- |
| 401 في المصدر | sik مفقود، غير صحيح أو ملغى؛ صحح الإعدادات |
| 400 في المصدر | الجسم خارج العقد؛ أزل الحقول الإضافية |
| 401 في الحالات | توقيع قديم، انتهاء صلاحية، مطالبات غير صالحة أو جلسة ملغاة |
| 400 في الحالات | سياق إلزامي غير صالح، تواريخ/حالات غير صحيحة أو تجاوز الميزانية |
| 403 من السياق | userState لا يتطابق مع المستأجر/الشخص في JWT |
| 404 في المحادثة | المورد غير موجود أو ينتمي لهوية أخرى؛ لا تفرض الوصول |
| 429 | الحد الأقصى؛ تراجع/تذبذب، بدون حلقة إصدار |
| 500/502/503 | فشل البنية التحتية، النموذج أو السياق؛ أبلغ عن عدم التوفر و requestId |
| 501 في الإجراءات/التصعيد | وظيفة بدون منفذ/موصل؛ استخدم قناة بشرية حقيقية |
| Chat يعمل، MCP لا يعمل | تحقق من القائمة المرسلة في الإصدار الأخير، الصلاحية، الجمهور واستجابة الكتالوج. |
| أداة مفقودة | تحقق من الكتالوج المتاح للرمز المميز المفوض واتصال الخادم. |

لا تستخدم فقط HTTP 200 كقبول: تحقق من محتوى الاستجابة واللقطة. الإنشاء الذي يفشل بعد حفظ الحالة قد يترك حالة بدون استجابة؛ لا تفترض معاملة تتضمن استدعاء النموذج. يجب أن تكون المحاولات محدودة ويتم إبلاغ المستخدم بها. سجل الطريقة، المسار المعلم، status، requestId والوقت UTC؛ لا تلتقط أبدًا Authorization/JWT، السر أو الحمولة الخام لإعادة توجيه التشخيص.

## 15. قبول إلزامي

1. مسار التمهيد بدون تسجيل دخول مرفوض قبل المصدر. الهويات المزورة لا تغير المستخدم المصادق عليه.
2. الإصدار بالاعتماد الصحيح يعيد المستأجر المتوقع و 900 ثانية؛ السر لا يظهر في المتصفح/الإعادة/السجلات.
3. JWT القديم مرفوض. الجلسة الجديدة تنشئ محادثة مع لقطة واستجابة حقيقية؛ تعيد الفتح لنفس الشخص.
4. شخصان من نفس المشروع ومستأجران: GET حالة و POST رسائل/ملاحظات/إغلاق/تصعيد/إجراءات لا تتقاطع الهويات.
5. السياق بدون كتل، هوية مختلفة، تاريخ غير صالح وحجم زائد مرفوضة؛ الأسرار الاصطناعية لا تستمر في اللقطة.
6. التجديد بعد 15 دقيقة، تسجيل الخروج أثناء التجميع، تغيير الحساب/الشركة/الدور والتصفح لا يستعيد محادثة شخص آخر.
7. النموذج يستجيب باستخدام الأدلة ويحترم حد التشخيص؛ الفشل لا يولد نجاحًا ظاهريًا.
8. أصدر جلسات بصفر وخادمين. تحقق من أن كل وجهة تتلقى الرمز المميز الخاص بها.
9. MCP يرفض الرمز المميز الخاطئ/القديم، المستأجر الخاطئ، المستخدم الغائب/غير النشط ومورد شخص آخر. اختبر معرف الجلسة المعاد استخدامه، إذا كانت هناك جلسة.
10. تأكد من أن التغييرات تتطلب تأكيد الاقتراح ولا تتكرر في حالة انتهاء المهلة.
11. CORS/CSP، الهاتف المحمول، لوحة المفاتيح والقناة البشرية معتمدة. تم اختبار التدوير المنسق في الاعتماد.

`node --test examples.test.mjs` بيتحقق من المحولات المعزولة باستخدام الـ mocks. ده مش بيحل محل اختبارات الـ end-to-end. املى `ACEITE.md` بالمسؤولين، الإصدارات، الأوقات، والأدلة بدون أسرار.

## 16. النشر، القطع، والاسترجاع

ثبت بيانات اعتماد التكامل، انشر الـ bootstrap والـ SDK، تحقق من الـ chat، واعتمد السيرفرات المعلنة في الجلسات.

ماترجعش تشغل الاشتراكات القديمة أو تحويل الـ MCP العالمي عشان تسترجع التوفر. لو حصل فشل، عطل الـ widget أو الـ MCP بتاع الـ tenant المتأثر مؤقتًا، وخلي القناة البشرية شغالة لحد ما تصلح المحول. ماتمسحش المحادثات عشان تتجنب 404 بتاع المالك.

سجل حدود الاحتفاظ والأدلة الخاصة بتطبيقك.

## 17. الملاحظات وملفات الحزمة

رجع اسم المشروع، الـ tenant، الـ commits بتاع الـ backend/frontend، تاريخ UTC، SDK/hash، بيانات الاعتماد المثبتة (نعم/لا، بدون قيمة)، الـ chat الموافق عليه، الـ MCP الموافق عليه/المتوقف، الاختبارات السلبية، القناة البشرية، والمعلقات. ماتنهيش بـ "يبدو أنه يعمل".

العدة العامة فيها الدليل ده بـ Markdown، الـ schema بتاع السيرفر، الـ fixture الأدنى، محول المصدر، مصادقة MCP، متحكم الـ frontend، SDK، الـ prompt، الاختبارات المعزولة، قائمة التحقق، عقد الإجراءات، والـ manifesto بتاع SHA-256. الحزم الفردية ممكن تضيف مرفقات محددة. الأمثلة مش بتنفذ تلقائيًا الـ endpoints بتاع تطبيق العميل. النسخة اللي ممكن تتصفح موجودة على https://support-ai.pontes.uk/developers?lang=arz.
